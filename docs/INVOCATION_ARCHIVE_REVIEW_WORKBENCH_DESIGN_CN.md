# 调用归档审查工作台设计

## 1. 目标与边界

调用归档用于在命中归档策略时保存有限期、加密的网关请求/响应副本，供平台管理员排障和审查。本次将其收敛为一个稳定的审查工作台：管理员能在不中断调用链路的前提下浏览、筛选、刷新、查看和删除归档记录。

本次不改变网关捕获时机、加密方式、归档范围优先级、保留期或队列“满时丢弃归档而不影响用户请求”的原则。

## 2. 页面结构

### 2.1 唯一标题来源

`AppHeader` 已依据路由 `titleKey` 和 `descriptionKey` 渲染页面名称与简介。因此功能视图不再重复渲染标题和描述。视图首屏只保留：

- 标签导航：归档记录、归档策略、运行态；
- 统一的刷新控制和最近同步状态；
- 与当前标签页对应的工作区。

顶部独立“设置”按钮移除。归档策略标签页是唯一、可见且无需跳转的配置入口。

### 2.2 手动刷新

手动刷新必须更新用户实际正在看的数据，而不是只读取运行态：

- 记录列表：保留当前筛选、页码、每页数量；
- 运行态：更新队列深度、成功/丢弃/失败和清理计数；
- 策略：仅在没有未保存草稿时同步，绝不覆盖本地编辑。

刷新过程复用现有数据，不以空 loading 行替换已显示表格；首次加载失败或首次加载中仍显示明确状态。后台响应通过单调请求序号收敛，较旧的响应不能覆盖新分页或新筛选结果。

### 2.3 自动刷新

自动刷新是页面本地行为，不写入服务器配置：

- 周期固定为 15 秒；
- 仅 `document.visibilityState === 'visible'` 时执行；
- 正在手动刷新、查看载荷、删除记录、加载详情或编辑未保存策略时跳过；
- 页面重新变为可见时立即执行一次安全刷新；
- 组件卸载时清理 interval 与 `visibilitychange` 监听；
- 自动刷新保留当前选择，只剔除已不在当前结果页的记录 ID。

页面显示“自动刷新（15 秒）”与最近成功同步时间，让刷新有可感知反馈。

## 3. 管理员直接查看

### 3.1 授权模型

直接查看仍是高敏感操作：

1. 管理员路由与现有管理员鉴权不变；
2. 现有 TOTP/二次验证 middleware 不变；
3. `direct_view_enabled` 仍是归档策略中的显式开关；关闭时只返回元数据；
4. 查看响应继续携带 `Cache-Control: no-store`，载荷不进入列表、URL、localStorage 或持久化前端状态。

本次取消的是“人为填写理由”这一摩擦，而不是取消鉴权、二次验证、加密或审计。查看接口可接受空 POST；服务端不会将调用者提供的任意自由文本作为查看理由持久化。

### 3.2 访问证据

每次尝试直接查看仍向 `invocation_archive_access_logs` 写入：归档记录 ID、管理员 ID、结果、客户端 IP、User-Agent 和时间。`reason` 字段保留为兼容列并记录为空；前端不再显示或要求它。载荷删除后访问证据依旧可查询。

结果保持区分：`revealed`、`direct_view_disabled`、`expired`、`unavailable`、`decrypt_failed`。这使管理员可以区分正常查看、策略拒绝、过期和解密失败，而不暴露正文。

## 4. 数据契约

### 4.1 前端 API

`revealRecord(id)` 改为无理由参数并发送空 POST。记录、策略、运行态和访问日志 API 的 URL 保持不变，避免影响现有路由、审计白名单或外部调用。

### 4.2 后端 API

`POST /api/v1/admin/invocation-archive/records/:id/reveal` 不再绑定 `reason` 请求体。服务层移除理由长度验证，但继续校验管理员身份、策略开关、保留期、密文状态和解密结果，并在每个结果分支写访问证据。

## 5. 可靠性和可用性

- 记录刷新不会清空已加载行，减少视觉闪烁；
- 刷新异常保留上一份可用数据，并显示局部错误；
- 任何敏感动作完成后会刷新记录与运行态；
- 自动刷新不影响未保存策略或详情对话框中的明文；关闭详情立即清除内存中的明文；
- 所有文本在中英文 locale 中同步，避免出现原始 key。

## 6. 验收标准

1. 页面只显示一组“调用归档”标题和说明；没有顶部设置按钮。
2. 手动刷新更新记录、运行态和安全的策略快照；有明确反馈。
3. 页面可见时每 15 秒刷新，切到后台和卸载后停止；刷新不清空筛选、分页、选择和已显示行。
4. 管理员完成二次验证后可直接查看载荷，无需填写理由；访问日志仍产生一条可追溯记录。
5. 被禁用、过期、不可用、解密失败的状态仍正确返回且不泄露载荷。
6. 后端单元/集成覆盖无理由查看与访问证据；前端 API 与类型检查、构建通过。

## 7. 有意不纳入本次变更

全文正文检索、批量导出、法律保全、第三方 SIEM 推送和更细粒度的审查角色需要独立的合规、容量和权限设计。本次不伪造这些能力；现有加密、范围策略、保留期、删除和访问审计构成可继续扩展的正确底座。

## 8. 载荷阅读与编码诊断

归档正文的原始值不可被前端“修复”或覆盖。阅读工作台在本地内存中派生展示副本，提供结构化、格式化和原文三种视图：JSON 使用稳定缩进；JSON Lines 与 SSE 逐条展开；OpenAI 兼容的 `messages`、`input`、工具调用和工具结果可按角色卡片阅读。所有展示都使用文本插值，不使用 `v-html`，因此归档中的 HTML、脚本或工具输出不会执行。

网关继续捕获原始字节。UTF-8 无效的正文以 Base64 加密保存；后端保留可信 `Content-Type` 中的 `charset` 参数而不保存完整请求头。前端可按声明字符集自动解码，也可由管理员在本地切换 UTF-8、GB18030、Big5、Shift_JIS、Windows-1252、UTF-16LE/BE 预览。原始 Base64 始终可查看和复制。

若正文已包含 Unicode 替换字符 `U+FFFD`，说明字节在进入归档前已经被上游转换丢失；工作台明确提示该情况而不伪造恢复结果。对于典型的“UTF-8 被单字节解码”痕迹，只提供显式的本地尝试修复视图，绝不自动替换原文或写回归档。

格式化受 2 MiB 上限和结构化条目上限保护，避免管理员打开合法但超大的归档时阻塞页面。超限时仍可查看与复制原文。字符集选择、展示模式和明文均不写入 URL、localStorage 或服务端。

## 9. 工具调用与 WebSocket 完整性

归档的权威内容始终是加密的原始请求/响应字节，不以解析出的“工具摘要”替代或覆盖它。完整模式下：HTTP 请求中的 `messages`、`input`、`tool_calls`、`function_call_output`、`custom_tool_call_output`、`mcp_tool_call_output` 等内容与 HTTP 响应正文一并保存；Responses WebSocket 的每个 turn 保存已接受的请求载荷（包括用户提交的工具结果）以及每一个成功写回客户端的下行帧。

WebSocket 响应不会再只把多条消息无边界拼接。归档密文中保存一次连续原始字节，并保存帧顺序、文本/二进制类型、写入时间、字节偏移、原始长度、已捕获长度和截断状态。载荷查看接口仅在管理员直接查看后从同一份原始字节派生帧视图，因此不会在数据库中重复存储大段工具输出。二进制帧以 Base64 只读展示，文本帧可进入相同的结构化阅读器。

阅读器覆盖 OpenAI Chat/Responses、Anthropic `tool_use`/`tool_result`、Gemini `functionCall`/`functionResponse`，以及 SSE、NDJSON 中的工具事件。工具调用显示名称、调用 ID、参数；工具结果显示关联 ID 和完整输出。解析失败、不认识的协议字段或超过结构化显示上限时，原始与格式化视图仍保留完整已捕获正文，不会因为展示器不认识某个工具而丢弃数据。

归档仍有两项故意可见的可靠性边界：管理员可把请求和响应的捕获上限设置到 256 MiB；超过所选上限会明确标记 `truncated`，而不会伪造完整性。WebSocket 最多保存 4,096 条帧边界元数据以防恶意的极小帧耗尽内存；在该极端情况下连续原始字节仍按所选正文上限保存，页面会明确提示帧边界目录已到上限。请求头、Cookie、API Key 与上游凭据继续不进入归档范围。
