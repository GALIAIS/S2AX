# 城市模拟引擎底座硬化设计与验收

版本：v1.2（2026-07-18）  
适用引擎：`city-f5-v1`、`city-f6-v1`、`city-f6-v2`、`city-f6-v3`  
状态：已实现；长期黄金回放作为发布门禁保留

## 1. 目标

本轮硬化不增加银行、信贷、股票或游戏玩法，而是确保城市本体可以在不破坏旧世界的前提下持续扩展。底座必须同时满足：

1. 旧引擎继续运行，新引擎不能静默接管旧世界。
2. 升级可预演、可审计、原子提交；失败不能留下半迁移投影。
3. 正向执行、规范状态、快照、重放和恢复使用同一版本声明。
4. 任一世界失败不能污染其他世界；失败尝试可观测且不伪装成成功 tick。
5. 长时间运行、进程重建和完整重放后仍保持金额、库存、人口和状态哈希一致。
6. 新子系统必须声明依赖与执行位置，不能通过任意 SQL 或旁路余额接入。

## 2. 版本契约

### 2.1 代码目录

引擎定义是代码中的不可变清单。每个版本声明有序子系统：

| 版本 | 子系统顺序 | 规范状态 |
| --- | --- | --- |
| `city-f5-v1` | control → ledger → resources → markets | 不含人口日历 |
| `city-f6-v1` | control → ledger → resources → calendar_demography → markets | 包含人口日历 |
| `city-f6-v2` | control → ledger → resources → calendar_demography → markets | 包含人口日历与人口迁移投影 |
| `city-f6-v3` | control → ledger → resources → calendar_demography → markets | 增加独立家庭数量与家庭 movement 投影 |

定义加载时验证以下依赖图：

- control 必须存在且最先提供控制语义；
- resources 依赖 ledger，且不能在 ledger 之前；
- markets 同时依赖 ledger 与 resources，且不能在二者之前；
- calendar_demography 必须位于 resources 之后、markets 之前；
- 未知、重复、逆序或缺失依赖的阶段拒绝启动。

命令归属也由版本契约检查。控制、总账和实物命令只能提交给包含对应阶段的世界；人口迁移命令还要求世界明确运行 `city-f6-v2`，不能仅凭存在 calendar_demography 阶段进入 v1。升级边界遗留的未知命令在 tick 内稳定拒绝，不会误落入控制命令分支。

### 2.2 数据库目录

`city_engine_versions` 与 `city_engine_upgrade_paths` 是不可修改的发布事实，分别保存支持版本和允许的单向升级路径。数据库目录不替代代码算法，而是防止：

- 世界写入一个服务器不认识的随意版本；
- 从新版本降级到旧版本；
- 绕过审计直接修改 `city_worlds.simulation_version`；
- 删除或原地篡改已经发布的版本与路径定义。

版本发布遵循“只追加”原则。修正规则必须新增版本和迁移路径，不能修改已产生 tick 的旧算法。

## 3. 显式升级协议

### 3.1 前置条件

- 操作者是世界 owner；
- 世界处于 paused；
- 源、目标版本存在且路径已发布；
- 当前 tick 有完整、哈希一致的源版本快照；
- 同世界升级由 advisory transaction lock 串行化；
- 请求带稳定 `Idempotency-Key`，相同键不同意图返回冲突。

### 3.2 事务流程

1. 锁定世界与源状态。
2. 建立或验证当前版本基线快照。
3. 写入 `running` 升级审计。
4. 建立 savepoint，并开启只对本升级审计有效的数据库写门。
5. 构建目标版本投影并执行全部目标不变量。
6. 生成目标版本规范 JSON 与状态哈希。
7. dry-run 回滚 savepoint，审计终态为 `planned`。
8. apply 模式写入同 tick 的目标版本基线快照，再一次性终结为 `applied`。
9. 任一步失败回滚 savepoint，源世界、源哈希和源快照保持不变，审计终态为 `failed`。

数据库在升级审计终结时再次核验：

- 源快照版本、tick、哈希与升级前世界一致；
- applied 的目标快照版本、tick、哈希与升级后世界一致；
- planned/failed 没有改变源世界；
- 只有 `running → planned|applied|failed` 一次终态转换，之后不可更新或删除。

### 3.3 历史读取

升级不会覆盖源版本快照。同一 `(world_id, tick)` 可以同时存在 F5 与 F6 基线，读取接口可显式指定 `simulation_version`。F6 重放从升级基线开始，不伪造升级前不存在的 F6 历史。

## 4. Tick 原子性与失败隔离

单步执行边界保持为一个数据库事务：

```text
世界锁
  → 版本/命令契约检查
  → 命令、总账、实物、人口、市场阶段
  → 世界投影与规范哈希
  → tick/event 不可变事实
  → 同版本 tick 快照
  → 提交
```

快照、journal、resource operation、population movement、market settlement 或状态哈希任一环节失败时，整个 tick 回滚。失败 tick 不产生 tick、event、快照或部分投影。

`city_tick_failures` 在原事务回滚后通过独立短事务记录 5xx 引擎失败。输入错误、权限失败、预期 tick 冲突和幂等冲突不计入引擎故障指标。失败事实不可修改；同一幂等键在根因解除后可以安全重试并只产生一个成功 tick。

世界锁以 world ID 为粒度。一个世界的失败或长事务不会取得其他世界的锁，其他世界可继续推进。

## 5. 守恒链长期缺陷修复

长期运行门禁暴露并修复了两个短场景难以发现的问题：

1. 一个经济周期包含多个 journal，周期计划曾复用首次加载的账户余额与版本。现在每个 journal 封账后把 entry 的前后余额和版本同步回锁定账户引用；下一 journal 必须从刚刚封账的版本继续，链不连续立即失败。
2. 比例分配在总量为零时曾返回空映射，导致就业或住房旧投影没有被清零。现在结果始终包含所有输入 key 的显式零值，并拒绝重复 key，零需求和零支付能力也会形成完整投影更新。

这两项修复都保留整数守恒、版本检查和确定性排序，不通过放宽数据库约束掩盖问题。

## 6. 运行观测

世界引擎信息接口返回：

- 运行版本、当前服务器版本、世界状态、当前 tick 和状态哈希；
- 有序阶段、允许升级目标和是否可写；
- 待处理命令数；
- 当前版本快照数量与压缩字节数；
- 最近 tick 耗时与完成时间；
- 真实引擎失败次数、最近错误码与发生时间。

这些数据来自数据库事实，不从前端测试数据或进程内计数器推断。

## 7. 发布门禁

### 7.1 必跑自动化

- 版本图、命令归属和规范状态形状单元测试；
- 迁移结构与不可变触发器测试；
- F0–F6.1 组合集成测试；
- F5/F6 并存、dry-run、apply、历史快照和升级失败回滚；
- 同世界并发串行化、跨世界失败隔离；
- tick 快照故障注入与相同幂等键恢复；
- 目标快照故障注入与升级重试；
- 10,000 tick 固定种子黄金运行、5,000 tick 处重建服务实例、0→10,000 全量重放；
- 最终账户非负约束、库存非负约束、人口与就业边界检查。

长期门禁通过环境变量显式开启：

```text
CITY_ENGINE_LONG_RUN=1 go test -tags=integration ./internal/repository \
  -run TestCityEngineTenThousandTickGoldenReplay -count=1 -timeout=45m
```

### 7.2 新版本准入

任何 F6.2 或更高版本必须同时提交：

1. 新引擎定义及依赖图测试；
2. 只追加数据库版本与升级路径；
3. 源→目标 dry-run/apply/失败注入测试；
4. 新规范状态编码与旧版本编码不变测试；
5. 正向事实、重放归约和恢复映射；
6. 至少一个跨边界长期黄金场景；
7. 守恒、上限、溢出和幂等测试；
8. 运行指标与容量基线。

缺少其中任何一项，只能作为实验分支，不能把 `CurrentCitySimulationVersion` 指向该版本。

## 8. 扩展边界

底座现在允许通过“新版本 + 新事实 + 新投影 + 新归约器”增加人口迁移、家庭演化、空间、交通、设施、产业、环境等城市本体模块，但“可扩展”不等于运行时任意插件直接写库。每个模块必须：

- 声明稳定 stage code、依赖和执行顺序；
- 接收模拟时钟和版本化随机源，禁止读墙钟；
- 使用整数/定点数和明确舍入；
- 先写不可变事实，再通过受保护函数更新投影；
- 把状态加入该新版本的规范编码；
- 提供同序重放与 verified recovery；
- 通过世界事务与 savepoint 隔离预期业务拒绝；
- 不引用平台余额作为城市内部事实来源。

银行信贷与证券仍是城市经济的可选分支，只有在企业、家庭、财政和长期运行指标稳定后才接入；它们复用总账、版本、事实和重放边界，但不反向成为城市基础内核的必要依赖。

## 9. 尚未宣称完成的产品运行层

本轮完成的是单世界确定性内核与版本生命周期；F6.3 已按相同协议接入，F7.0 已完成不改变世界状态的空间规则/坐标底座。这不等同于整个游戏产品已经成熟。以下仍需独立阶段实现：

- 后台多世界调度、租约续期、失败退避、隔离队列和运维控制台；
- 增量/分层快照、保留与归档策略，以及大世界恢复时限；
- 指标时序聚合、告警阈值和容量压测报告；
- 奖励 outbox/inbox 与平台虚拟货币的端到端对账；
- F7.1 Overmap/Chunk 世界状态、地块建筑及更高层城市本体玩法。

这些功能必须建立在本文件的版本、原子性、守恒和回放门禁之上，不能另起一套状态机。
